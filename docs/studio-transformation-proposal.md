# A1O Platform：Studio 化评估与分阶段改造建议

日期：2026-10-31；运行时方向更新于 2026-11-01。状态：产品方向已确认，具体实现方案待验证，尚未实施；本文不修改当前运行契约，也不授权删除现有能力。

2026-10-31 决策更新：用户已确认分设 Chat / Work，面向云端多任务场景；智能体广场包含内置智能体与用户自己创建的智能体，不做智能体销售。本决定替代此前“统一对话入口”的建议。界面分开，身份、模型、工具、运行内核、计费和素材底座共享；代码执行环境按需分配。

面向产品负责人和后续实现者。目标是形成以 AI 使用、创作和复用为中心的平台，同时保留 API 网关。已确定的用户要求：DeepL 独立翻译界面、图像生成、参考 Google AI Studio、重构现有 Chat 运行时，以及上述 Chat / Work 和智能体广场范围。其他新增功能、数据结构及阶段划分属于建议。

2026-11-01 方向更新：用户要求参考 Hermes、Cherry Studio、ZCode，重构为真正的 Agent 运行时，并考虑自研与 OpenResponses。当前建议采用 Go 自研内核及 OpenResponses 标准结构，替代此前 Eino 迁移建议。详细范围、协议边界、迁移与验收见 [Agent 运行时重构方案](agent-runtime-reconstruction.md)；具体实现仍未完成。

原 2026-10-31 评估时工作区存在大量未提交的 relay/controller/router 改动，该部分是当时快照。适配器随后已单独改造并提交；当前协议实现情况以 `adapter-protocol-audit.md` 和代码为准，不能把下表的旧适配器状态当作最新结论。没有运行应用、测试、真实上游调用或数据库迁移，没有下载依赖。已有文档中的“已验证”是历史记录，不代表本次复验。

已在浏览器查看 Google AI Studio 公开欢迎页及其视觉布局；聊天入口跳转到 Google 登录，未访问登录后的工作台。工作台参数面板、提示词试验与代码导出等参考来自官方文档，不宣称完成登录后 UI 的实测。来源见文末。

## 2. 当前项目与目标的距离

| 层面 | 当前代码证据 | 对改造的含义 |
| --- | --- | --- |
| 技术栈 | Go/Gin/GORM；React 18、TypeScript、Vite、Semantic UI | 保留现有技术栈与单体部署即可开展 Studio 改造，无须先拆微服务 |
| 入口 | `web/default/src/App.tsx` 和 `components/Header.tsx`：管理、聊天、图像、决策等入口；`chat/api/both` 导航偏好 | 已有用户使用入口，但仍以管理台导航为主；偏好不是权限边界 |
| 对话 | `controller/chat.go`、`model/chat.go`：会话、消息、文件、Skill、MCP 持久化；SSE 请求驱动运行 | 可作为 Studio 对话基础；不需要先重写存储 |
| Agent | `chat/runtime.go` 手写工具循环；`chat/context.go` 上下文与摘要；`chat/tools.go` 工具筛选 | 新 Agent 内核替换编排，历史、权限和产品事件仍由平台管理 |
| 调用底座 | `chat/leg.go` 经 `lifecycle.Forward`；原生与服务商路径还有 `ForwardAdapter` | 必须复用路由、协议转换、订阅账号、预扣/结算和日志，避免运行内核绕过网关 |
| 图像 | `pages/Playground/ImagePlayground.tsx`：用户选令牌、输入模型和参数，调用 `/v1/images/generations` | 图像生成已经存在；需升级为创作工作台、持久历史及素材管理 |
| DeepL | `relay/adaptor/deepl`：最后一条消息转文本；模型名拆分得到目标语言；只传 text/target_lang；`len(text)` 写入 token 用量 | 缺独立翻译契约；Go 字符串长度是字节数，不能当作可靠的上游计费字符数 |
| 后台任务 | `relay/background/store.go`：Responses 任务存在进程内存，带数量上限和 TTL | 不能直接当作 Studio 的持久任务系统；现有 Responses 查询/取消契约须保留 |
| 并发 | 聊天控制器用进程内 `sync.Map` 防止同会话重复运行 | 多实例部署若共用会话，需要数据库租约或等效跨进程互斥 |

文档有时间差：`docs/builtin-chat.md` 写“不隔离网络”和 `sh -c`，当前 `chat/sandbox.go`、`sandbox_linux.go` 使用 prlimit、可选网络命名空间，并在隔离不可用时拒绝执行。方案以实际代码作为行为证据；仍不能据此宣称具备文件系统/多租户强隔离。实现阶段应同步更新该文档，保留 Python/Node 执行能力。

## 3. 产品结构：创作入口、开发者入口和管理入口

建议保留 A1O Platform 产品名，以 Studio 作为登录后的主要使用工作区。公开首页介绍能力；现有用户的落地偏好迁移后保留，允许切换工作区。

建议导航：

- Studio：概览、Chat、Work、智能体广场、图像创作、DeepL 翻译、素材与历史。Chat 展示对话历史，Work 展示任务列表、执行进度和成果；智能体广场分“内置”和“我的”。
- 开发者：API 密钥、接入指南、API 调试、SystemOne 决策 Playground、用量日志。
- 管理：渠道、上游账号、用户、全局 Skill/MCP、计费配置、系统设置。
- 账户：个人设置、余额与充值；用户在 Studio 内也能查看自己的消费明细。

这些是信息架构分区，不是三套账户或三套后端。导航隐藏不代替服务端授权。旧 `/chat`、`/playground/image`、`/playground/decision` 等地址继续可达；先保留原页面，等价迁移后才设路由别名或重定向。

从 AI Studio 借鉴的重点是“选择任务 → 输入/调参 → 运行 → 查看结果 → 保存/复用”，以及功能与参数分层呈现。其公开页的模型能力卡片适合用于概览；营销页的大幅动态视觉不直接照搬到高频工作区。模型名称和供应商不是用户完成任务的前置知识。

建议桌面布局为左侧固定导航、中间工作区、右侧可折叠参数栏。对话的会话列表置于导航内的二级区域，避免额外常驻第四栏；小屏采用抽屉。视觉上统一间距、字号、边框、状态色和浅/深色主题，减少管理表单式堆叠。暂不因改版替换整个组件库，先隔离 Studio 样式，避免破坏管理页。

概览应直接提供“开始聊天 / 新建任务 / 生成图像 / 翻译文本”和最近记录。Work 主区展示目标、任务状态、步骤及成果，右栏展示预算和执行资源；不把执行日志全部堆成聊天气泡。对话工作区展示消息、可折叠工具执行记录、附件及输出产物；右栏配置模型、系统提示词、工具与 Skill、预算。运行结果提供真实用量和耗时；估价明确标记为预估。API 示例是可选开发者操作，不占据普通用户主流程。

用户可选通用助手、内置智能体或个人智能体。Chat 默认轻量运行，不创建代码执行环境；需要持续执行时，用户通过“转为 Work 任务”选择携带的上下文、工具和预算，创建关联任务并进入 Work，原对话保留。运行中的请求不静默转换类型，也不隐式扩大工具权限或费用上限。Work 仅在实际需要且授权执行代码时分配沙箱；搜索、翻译、模型/API 调用不因此启动沙箱。智能体定义、对话记录、任务执行是不同对象，详见第 12 节。

首期不默认新增可视化 Workflow 编辑器、应用托管发布、团队协作、RAG 或多 Agent。它们是后续可评估扩展，不是已确认功能的前提。云端并发执行多个独立任务也不等于多 Agent 编排。

## 4. 后端边界与最小共享基础

建议维持单体，在现有包附近逐步提取以下逻辑边界；目录名只是建议，不能作为删除范围：

```text
Studio UI / 现有 API 客户端
    ↓ 登录态接口 / 令牌接口
应用服务：Chat、Work、智能体配置、图像、翻译、素材、运行记录
    ├─ Chat → 交互运行 → 共享 Agent 内核 / 模型与受权工具
    ├─ Work → 持久队列 / worker → 共享 Agent 内核 / 模型与受权工具
    │                              └─ 代码工具按需申请隔离沙箱
    ├─ 图像 → ImageService
    └─ 翻译 → TranslationService
                ↓
共享渠道选择 / lifecycle / 计费 / 日志 / 凭据
                ↓
模型与服务商
```

Studio 的图像与翻译走专用应用服务，无须让 LLM 先决定调用什么。后续 Agent 可通过工具包装调用同一服务，从而共享权限、产物和计费。

登录态请求的用户身份从服务端会话取得。初期可以沿用隐藏内部令牌机制承载计费身份，但不向浏览器暴露其密钥；也不要求用户手动创建 API Key 才能翻译或画图。现有 API 调试页继续允许选择个人令牌。新接口必须继承现有登录态写操作防护，并按资源 owner 校验访问。

需要先增加模型/服务能力目录，区别于当前只返回模型名的列表：输入/输出模态、支持的 operation、工具调用/流式能力、参数 schema、限制、计价单位。能力必须与用户分组、可用渠道及模型映射共同求交；未知能力不能凭模型名字猜测。执行时按所选 operation 和参数重新筛选渠道，回退时也不得转到不支持该能力的渠道。

建议持久对象：

| 对象 | 首期用途与边界 |
| --- | --- |
| 现有 ChatSession/ChatMessage | 继续作为对话事实记录；保留主键、owner、附件和 tool_call 关联 |
| StudioRun | 记录一次操作的 owner、kind、状态、输入参数快照、模型、错误、时间、幂等键；对话可关联已有会话，先不重建消息表 |
| WorkTask | 持久任务的 owner、目标、输入快照、预算、队列状态、关联 run、worker 租约；明确任务与执行尝试的关系 |
| RunStep / 消费关联 | 记录多轮模型与工具步骤，关联已有消费日志；汇总展示费用，不另起一套重复扣费账本 |
| Asset | 上传文件或生成图像的 owner、MIME、大小、存储键、来源 run；不把 base64 图像塞入消息文本 |
| TranslationRecord | 源/目标语言、输入/输出文本、参数、实际计费字符数、关联 run；与聊天消息分开 |

上述名称是拟议数据契约。首期不需要组织/项目多租户模型；现有用户隔离继续生效。旧 ChatFile 先通过引用接入素材展示，不直接移动或删除原文件。增加引用关系后才能设计回收：删除会话不得误删仍被其他记录引用的素材。生成记录与消费记录的保留策略分别制定，不连带删除账务。

Work 调度应设用户级和全局并发上限、排队状态、步数/时长/费用预算，以及 worker 心跳与租约。多任务并行不改变单个任务内部默认顺序执行工具的语义。代码环境只在实际代码工具调用前申请，按任务隔离；结束、取消或空闲超时后释放，释放前把需要保留的产物写入持久素材存储。Chat、图像和翻译直接调用模型/服务时不预分配代码环境。当前宿主进程沙箱不足以证明不可信公众代码的强隔离；面向该场景开放前，须验证独立沙箱执行服务及文件、网络、资源隔离，不将其当作模型协议自带能力。

新增表/字段采用可空关联和增量迁移。上线前在数据库副本上验证 SQLite/MySQL/PostgreSQL 的受支持部署路径、旧数据可读及回滚兼容；回滚应用时保留新数据，不用删表作为回滚手段。

## 5. Agent 运行时重构方案（替代 Eino 迁移）

2026-11-01 重新评估后，不再沿用“ChatModelAgent 替换手写循环、先统一 Chat Completions 再补原生能力”的路线。新建议是 Go 自研 Host / Engine / ModelExecutor / ToolExecutor / Scheduler，以 OpenResponses 的 Item 与模型事件为标准基础，保留供应商原生协议和不透明状态。OpenResponses 不是任务调度或持久执行框架，不能用它代替 Run、工具执行与工作区设计。

完整的职责、持久对象、状态、接口边界、KEEP/MOVE/REPLACE/DELETE 清单、实施顺序和验收以 [Agent 运行时重构方案](agent-runtime-reconstruction.md) 为准；其 R0–R4 替代本文件与运行时相关的旧 Eino 路线。Studio 的布局、DeepL、图像和广场产品范围继续按本文件，存在运行时实现解释差异时采用新方案。

新旧引擎切换前保留现有入口、工具权限、摘要、附件、历史及逐次模型调用计费；不对真实收费请求或有副作用工具双跑。旧 Chat 断开即取消，Work 离页继续；二者共享内核但冻结不同运行策略。新内核接通真实入口、完成原生模型往返及故障验证后才能移除旧私有循环，不以接口空壳作为完成标准。

## 6. DeepL 独立翻译工作台

建议路由 `/studio/translate`；双栏显示原文/译文，上方源语言（含自动识别）、目标语言和交换按钮，下方字符用量、复制、历史。自动识别尚无结果时不提供含糊的语言交换行为。首期采用显式“翻译”按钮，避免每次输入都发出付费请求。

建议新增登录态接口 `POST /api/studio/translations`，明确传递 `text[]`、`source_lang`、`target_lang` 及支持的可选参数；响应包含结果、检测语言、run id、计费字符数与扣费信息。语言/参数能力通过单独元数据接口返回，不能用 `deepl-XX` 模型名代替业务字段。

先支持文本翻译、自动检测、参数复用与持久历史。formality/context 等选项按目标语言和账号能力展示。术语表管理和文档翻译作为后续增强；文档翻译需要独立上传/任务/下载及计费设计，不以文本接口冒充支持。

上游请求设置 `show_billed_characters` 并读取实际计费字符数；context 不应混入收费文本用量。字符与 token 分别记录，既有额度仍作为内部余额单位。官方接口支持这些字段与 formality 等选项，具体语言能力按其元数据验证。[DeepL 文本翻译接口](https://developers.deepl.com/api-reference/translate/request-translation)。

新服务通过共享渠道与预扣/结算机制调用 DeepL，可借用 `ForwardAdapter` 模式，但需要新建明确的翻译 operation/usage 映射。旧 DeepL Chat 适配入口继续保留；其计量修正须明确影响、新旧价格映射和上线日期，不能静默改历史账单。上游计费用量缺失时使用已定义并实测的估算/待核对策略，不能直接沿用字节数冒充实际字符数。

验收：无需 API Key 即可翻译；中英文、emoji、多字节及区域语言标识正确传递；失败和上游限额错误可解释；重复点击同幂等键不重复调用；历史跨刷新可读且不可越权；实际字符用量与测试响应及账单一致。

## 7. 图像工作台

建议路由 `/studio/images`；以提示词、适用的尺寸/质量/数量选项、结果画布和历史缩略图构成主流程。保存生成参数、修订提示词及产物，支持下载和按原参数再次生成。先完成文生图；参考图编辑/局部重绘仅在后端已实现相应 operation 并验证目标模型后开放。

首期复用现有 `/v1/images/generations` 的 OpenAI wire 与 Replicate 服务能力，抽取为登录态 ImageService；明确保留现有价格规则，不能创建第二套彼此不一致的图片计费。未来接 Gemini 原生图像输出时另做适配，不能认为所有图像模型都接受 OpenAI Images 参数。

当前图像页面接受任意可用模型并给出固定参数列表，需改为按能力目录筛选。保留开发者调试页的自定义模型能力；普通创作页对未知能力给出明确状态，不把猜测参数发送给上游。

建议用持久 Run 驱动生成：请求创建 run，worker 领取执行，页面通过查询或事件观察状态。浏览器离开不隐式取消图像生成（新功能的明确语义，与既有聊天不同）；显式取消记录本地状态，上游不支持取消时说明仍可能产生费用。最初可用数据库任务表和同进程 worker，无需先引入新队列服务。

产物保存要覆盖 URL 和 base64 两类响应。URL 有效期不能等同于素材保留期；服务端取回图片需限制协议/重定向/目标地址、文件类型、大小和超时，防止 SSRF。数据库只保存元数据，文件写入已配置的持久媒体目录；多实例需共享存储方案。

Run 状态须区分“上游生成失败”“上游成功但保存失败”“执行结果待核对”。保存失败只能重试保存，不能自动重新生成并再次扣费。平台唯一 run/幂等键保证重复提交不重复执行；上游已受理但超时且不支持幂等/查询时，禁止盲目重试并承诺只收费一次。

验收：无需个人 API Key；过滤不支持的模型和参数；刷新后可查看任务和已保存图片；用户间不能访问素材；生成成功保存失败可独立重试；费用与原图像链路一致；旧图像调试入口仍可工作。

## 8. 能力保留与替换清单

这份清单针对已检查的入口与依赖，不代表所有间接调用已穷尽；每阶段实施前继续检索实际调用方、注册、类型及存储引用。

| 决策 | 对象 | 前置条件与验收 |
| --- | --- | --- |
| KEEP | 现有 `/v1`、`/v1beta`、SystemOne、Responses 后台查询/取消、音频/embeddings/审核、代理入口 | 原路由、认证与计费契约不因 Studio 导航调整而删除；相关回归通过 |

### 12.2 对 A1O 的最终产品方向

竞品证据表明界面分离并非统一标准，不能用厂商数量投票决定本项目结构。用户明确指出本项目主要部署于云端并服务多任务场景，因此采用独立 Chat / Work 入口；此前统一入口的建议已被这一决定替代。

| 边界 | Chat | Work |
| --- | --- | --- |
| 主要用途 | 问答、写作、翻译等简单交互，可使用获授权的轻量工具 | 需要持续推进的多步骤任务、数据处理和成果交付 |
| 展示对象 | 会话与消息 | 任务、状态、步骤、文件和成果；可附任务内对话 |
| 生命周期 | 等价迁移期保留当前请求断开即取消 | 持久任务，离页继续；可查询、重连与显式取消 |
| 资源分配 | 默认不创建沙箱或常驻 worker 任务 | 经队列和配额调度；仅代码执行步骤按需申请沙箱 |
| 智能体 | 使用支持 Chat 的内置或个人配置 | 使用支持 Work 的内置或个人配置 |

拆分入口本身不节省执行资源，必须落实到运行策略。当前 `chat/runtime.go` 只在会话和全局开关启用时暴露沙箱工具，`chat/sandbox.go` 在实际执行时才创建临时目录；不能把现状描述为每次聊天都启动沙箱。运行内核不应要求每个 Agent 配置沙箱。后续保留按需执行，并增加适合云端的队列、并发和隔离。

两种入口共享身份、模型网关、模型执行适配、工具、Skill、智能体配置、素材和计费；不复制两套实现。单次工具调用或生成文件不必自动升级为 Work。图像和 DeepL 的专用工作台直接调用应用服务，不因为产品采用 Chat / Work 就强制套入代码环境。

Chat 的“转为 Work 任务”创建新的持久任务，保存用户选定上下文的快照与来源会话引用；原会话不删除。运行类型在启动时确定并持久化，不能在执行途中静默变更。任务追加输入通过待处理输入队列在安全步骤边界消费，不能并发改写当前模型历史。已有会话显式启用的代码工具及既有 API 能力先保留；新 Chat 默认不启用，若以后限制旧入口须另行确认迁移范围。

P3a 验收必须证明：普通 Chat、非代码 Work、直接图像/翻译操作均不创建代码环境；代码 Work 只在授权步骤申请环境；不同用户/任务工作目录隔离；取消一个任务不影响其他任务；并发满额时正确排队；结束/取消后释放资源但保留持久产物；重启后核对任务状态且不盲目重复外部副作用。恢复到中断步骤继续执行须在 checkpoint 与幂等验证通过后开放，不能把“有状态记录”宣传为可自动恢复。

### 12.3 智能体广场：内置与自己创建，不做销售

理由来自项目本身：当前会话已经有模型、系统提示词、Skill、工具和附件配置，用户创建“论文助手”“运营报告助手”等可复用配置能减少重复设置。产品收益应通过重复使用率和任务质量验证，不能仅以竞品具备该功能论证。

需把三个概念分开：智能体定义“谁来做、遵循哪些规则、默认使用哪些能力”；Skill 定义“如何完成一类步骤”；任务记录“这一次做什么及执行到哪里”。个人智能体可以参与普通对话，也可以启动任务，不绑定成仅限 Work 使用。

用户确认广场包含内置与自己创建的智能体。具体第一版实现建议：

1. 一个智能体广场，包含“内置”和“我的”两个分区。管理员维护内置智能体，用户创建/编辑自己的智能体；配置包括名称、用途说明、指令、开场建议、默认模型、现有 Skill 绑定、工具范围、参考文件及默认运行预算。广场不等于其他用户公开发布的市场。
2. 表单配置与试聊预览为基础；自然语言辅助生成只生成草稿，用户可以查看和编辑。预览按实际模型/工具调用计费，并受与正式运行相同的权限与预算约束。
3. 保存可运行版本、复制获准复用的配置、从现有会话设置创建；从 Chat / Work 选择智能体，或从卡片打开对应入口。卡片标注支持 Chat、Work 或两者；保存配置、浏览卡片和普通试聊均不预创建沙箱。
4. 参考文件先复用现有受限附件上下文，明确大小、类型和上下文限制；不能把上传附件宣传成已经有 RAG 知识库。
5. 明确排除智能体售卖、购买、订阅销售与作者分成。现有模型/工具实际调用的用量计费保留，与销售智能体不是同一件事。其他用户公开发布、团队分享、长期记忆、定时执行、多 Agent 编排、可视化 Workflow 均不属于当前确认范围。

建议新增 AgentDefinition 与不可变 AgentVersion：定义记录 owner、名称、当前版本和归档状态；版本保存指令、模型/参数、Skill 版本或快照、工具引用、文件引用、支持的 Chat/Work 模式及按需执行资源策略。每个新 run 固定使用的 agent version 和有效配置快照，不把运行引擎的内存对象直接序列化为业务数据库结构。模型通过原网关，工具通过原 MCP/Sandbox 服务适配；无需为每个智能体启动独立常驻进程。

版本快照保存规则与引用，不保存明文凭据或复制参考文件到他人名下。实际权限是当前用户权限、智能体允许范围、管理员策略的交集；选中 Skill 的工具限制继续按现有语义生效。每次执行时检查文件与工具的当前授权，撤销授权即时有效，不能以旧版本快照绕过撤销。使用内置智能体时，工具须使用管理员明确授权的服务连接或使用者自己的连接，不能继承其他个人作者的密钥；内置配置不包含他人的会话历史与个人记忆。

归档/删除个人智能体默认阻止新启动，已有对话、运行、素材与消费记录保留可读；已有运行固定版本，若涉及权限撤销则按撤销策略停止相关步骤。编辑智能体不修改旧会话快照。旧 Skill 与会话不自动合并或删除；智能体调用还应保留可供未来 API 使用的服务边界，但首期不据此擅自新增公开发布契约。

P2a 验收至少覆盖：广场正确展示可见内置项与本人创建项；不能编辑内置项或读取他人的私有定义；新建后可在支持的 Chat/Work 真实入口运行（Work 依赖 P3a 开放）；配置复用而历史隔离；版本更新不影响在途运行；工具/模型/文件越权拒绝；Skill 限制保留；归档后历史可读；消费可归属用户/run；失败可解释。P3a 的持久任务验收还须覆盖进程重启后的状态核对，外部副作用不能自动重放，以及取消与费用结算的一致性。

### 12.4 范围与一致性说明

用户已确认分设 Chat / Work，以及包含内置和个人智能体的广场、不做销售；具体数据结构、交付顺序和后续可选能力仍属建议。原 DeepL 独立翻译、图像生成要求继续保留；Eino 替换路线已由 2026-11-01 的 Agent 运行时重构方案替代；第 3、4、8、9、10 节已同步产品决定。当前 README 和内置聊天文档描述已实现产品，本轮不把未实现规划写成既有能力。本轮只更新方案，没有业务代码、数据库或运行行为变更。
